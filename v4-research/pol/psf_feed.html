By supplying an admin username with an arbitrary API key the request was processed with admin privileges.</p> <p>If exploited, this would have allowed an attacker to modify Python release and file metadata that affects what URLs users are offered when visiting <a href="https://python.org/downloads">python.org/downloads</a>. While it would not enable existing release files to be modified in-place, it would enable an attacker to modify the URLs that are provided on <a href="https://python.org" rel="nofollow">python.org</a> for each release file, including verification material URLs. There is no evidence this vulnerability was exploited after auditing logs and database backups. This scenario is even more unlikely to have happened unnoticed due to the many redistributors requiring Python Sigstore and PGP materials be verified prior to builds.</p> <div class="markdown-heading"><h2 class="heading-element">Details</h2><a aria-label="Permalink: Details" class="anchor" href="https://gist.github.com/#details" id="user-content-details"><span aria-hidden="true" class="octicon octicon-link"></span></a></div> <p>PSRT confirmed the vulnerability on a local instance of python.org. <a href="https://sethmlarson.dev">Seth Larson</a> and <a href="https://hugovk.dev/">Hugo van Kemenade</a> developed and deployed <a aria-keyshortcuts="Alt+ArrowUp" data-hovercard-type="pull_request" data-hovercard-url="/python/pythondotorg/pull/2946/hovercard" href="https://github.com/python/pythondotorg/pull/2946">the patch</a> to production with help from <a href="https://github.com/jacobcoffee">Jacob Coffee</a>. Less than 48 hours after the initial report the PSRT and the reporter confirmed that the proof-of-concept provided by the reporter no longer worked locally or on the production deployment.</p> <p>This vulnerability was likely never exploited. However due to the age of the vulnerability (<a href="https://github.com/python/pythondotorg/commit/0be429f0213cc735084a81d9b5d2dcf56467849b#diff-79d93d354534ebbcabe21fac3845315a8efe1fa0350576810962b3cc50fa3f5cR12-R14">existing in the codebase since 2014</a>) we don’t have absolute certainty beyond our logs and database backups. We believe attempts to exploit this vulnerability would have been “loud” and discovered quickly given the number of downstream tools and distributions automatically verifying the Sigstore and PGP materials.</p> <p>We confirmed that all artifacts on python.org had not been modified by verifying Sigstore and PGP materials. Our own workflow verifying all Sigstore signatures did not signal any changes to artifacts from years prior. While verifying PGP materials we were able to verify all signatures where keys are still readily accessible from Python 2.5 to 3.13. Note that Python 3.14 and onwards <a href="https://peps.python.org/pep-0761/" rel="nofollow">no longer provide PGP materials</a>, so these were verified with Sigstore.</p> <p>The codebase was manually audited and additional hardening was applied. In addition to manual auditing, LLM auditing tools were unable to find additional issues with authentication. The delay between the initial finding and publishing of this final report was to give ample time for auditing for other issues related to authentication, to receive access to LLM auditing tools, and to arrange and complete a <a href="https://blog.trailofbits.com/2026/06/22/introducing-patch-the-planet/">third-party audit from Trail of Bits</a> prior to publication of this report. Full results from the Trail of Bit audit will be published soon.</p> <div class="markdown-heading"><h2 class="heading-element">Remediations</h2><a aria-label="Permalink: Remediations" class="anchor" href="https://gist.github.com/#remediations" id="user-content-remediations"><span aria-hidden="true" class="octicon octicon-link"></span></a></div> <ul><li>Patch applied and deployed to ensure behavior is not mixed between the “guest” authentication mode and API key authentication.
